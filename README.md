# EODReader (EOD Viewer)

Настольное приложение (Delphi 12 / FireMonkey, Win32) для просмотра и анализа
записей электрических разрядов рыб (EOD — Electric Organ Discharge).
Работает с 4-канальными записями, хранящимися как пара стерео-WAV, и с собственным
компактным форматом пиков `.eodpk`.

## Важные файлы для ИИ-агентов

Если над проектом работает ИИ-агент, **перед чтением или изменением кода обязательно обработать `AGENTS.md`, `TODO.md` и `HISTORY.md`**.

- `AGENTS.md` — обязательные правила работы с проектом.
- `TODO.md` — текущий план, порядок действий и список выполненных задач.
- `HISTORY.md` — история существенных изменений; особенно внимательно читать записи об изменениях логики обработки и математических расчётов.

После существенных изменений агент должен внести запись в `HISTORY.md`.

## Возможности

- Открытие пары WAV (Tr12 = каналы 1–2, Tr34 = каналы 3–4); чтение — в фоновом потоке.
- Фоновый анализ записи: STD по 4 каналам → FIR15-фильтрация → поиск пиков по
  prominence (O(N), монотонные стеки). Промежуточный прогресс и отмена.
- Сохранение найденных пиков в файл `.eodpk`.
- Просмотр `.eodpk`: малые диапазоны восстанавливаются точно из записей пиков,
  большие — рисуются из кэшированной огибающей (без аллокации полного буфера).
- Режимы отображения: `RAW - 4 channels`, `STD`, `FIR15`, `RAW + FIR15`,
  `RAW channels separate`, `IPI histogram`.
- Навигация: обзорный график (min/max, ~2000 бинов) с кликом и выделением диапазона,
  зум колесом, панорамирование, позиционный ползунок, список пиков (окно ±100 с
  с переходами `<<` / `>>`), кнопки Prev/Next.
- Обзорный график может рисоваться в цветах каналов (Ch1…Ch4) — включается
  свойством `ChannelColors` у контроллера обзора (`GUI.OverviewController`,
  класс `TEodOverviewController`); поканальные огибающие строятся воркерами обзора
  (Threads.Overview для WAV, Threads.PeakOverview для .eodpk — из кэша файла), поэтому переключение режима
  не перечитывает запись. Каждый канал масштабируется по своему максимуму.
- **Воспроизведение записи** (кнопка `Play`): плеер ведёт «виртуальное время»
  записи и показывает картинку очередного пика в тот момент, когда наступает его
  время — т.е. запись проигрывается в реальном темпе. Скорость 0.1x…10x выбирается
  рядом с кнопкой (1x = реальное время). Старт — с текущего выбранного пика;
  после последнего пика воспроизведение останавливается само. Ползунок позиции
  двигается вместе с «виртуальным временем».
- Настройки детектора в диалоге (Settings) с сохранением в JSON.

## Форматы данных

### Вход: пара стерео-WAV
`TFourChannelAudioSource` (IO.AudioSource) объединяет два стерео-WAV в один
поток 4-канальных кадров `TAudioFrame` (4 × Single). Чтение WAV — IO.WavReader.

### Формат `.eodpk` (версия 3)
Единицы: `IO.PeakStore` (`TEodPeakStore`). Раскладка файла:

```
Header (TEodPeakFileHeader: magic, version, SampleRate, PeakCount, TotalFrames,
        SamplesPerPeak, CacheOffset, ...)
UTF-8 source name 1
UTF-8 source name 2
Пиковые записи фиксированного размера          ← RecordOffset = DataOffset + Index * RecordSize
Cache header (magic 'EODCACH3')
Cache level 0 … N
```

- Каждая запись: `TEodPeakRecordHeader` (`Position`, `StartPosition`,
  `TimeSeconds`, `PeakValue`, `Prominence`, `SampleCount`) +
  `SamplesPerPeak × TAudioFrame` сэмплов окна вокруг пика (по умолчанию 30 до / 30 после).
  Фиксированный размер записи даёт прямой произвольный доступ по индексу.
- Позиции пиков отсортированы по возрастанию (на этом построены бинарные поиски).
- Кэш огибающей: страницы по `EodPeakPageSize = 5000` записей; уровни кэша
  группируются по 4 (`EodCacheGroupFactor`), максимум 16 уровней; каждый бакет —
  `TWaveEnvelopePoint` (min/max по 4 каналам). Кэш пишет `BuildCacheForStream`,
  читает `ReadEnvelope` при больших диапазонах отображения.

## Конфигурация

`config.json` рядом с exe (`Core.ConfigStore`). Поля — `TEodDetectorConfig`:
`PeakProminence`, `CorrelationThreshold`, `WindowBefore/After`,
`ExtractionBefore/After`, `ChunkSize`, `DuplicateDistance`,
`OverviewMaxSeconds` (лимит автоматического построения overview в секундах;
`0` отключает автоматический запуск). `ChunkSize` ограничен диапазоном
1024…1048576. Для больших WAV overview можно построить кнопкой «Обзор»;
при отсутствии/повреждении файла молча используются значения по умолчанию.

## Электродная геометрия и локализация рыбы (в разработке)

Подсистема `Electrode.*` реализует разметку взаимного расположения электродов
и локализацию рыбы по амплитудам 4 каналов. Статус: рабочая версия; каналы
записи (Ch1..Ch4) сопоставляются парам пользователем примерно вручную, а
полярность подбирается автоматически.

Модули:

- `Electrode.Geometry.pas` — аффинная калибровка (`hmAffine`) с нормализацией
  Хартли, опциональным уточнением методом Левенберга-Марквардта, моделью
  дисторсии с защитой от переобучения. Аффинная модель выбрана вместо
  проективной: калибровочные точки лежат только по периметру прямоугольника
  (аквариума), что делает проективную модель плохо обусловленной.
- `Electrode.Localization.pas` — локализация положения рыбы методом
  Левенберга-Марквардта по амплитудам 4 каналов, с мультистартовой сеткой
  (`LocalizeMultiStart`) для смягчения проблемы симметричной неоднозначности
  раскладки электродов.
- `Electrode.Matching.pas` — подбор соответствия «пара электродов ↔ канал
  записи» и полярности (+/-) перебором комбинаций с оценкой по невязке
  модели поля; локализует все переданные события выигрышной конфигурацией.
- `Electrode.Amplitudes.pas` — извлечение амплитуды EOD-события по каждому
  каналу из окна сырого сигнала вокруг события.
- `Electrode.Settings.pas` — запоминание последних путей (JSON разметки и
  картинка кадра) в `electrode_paths.json`, авто-подгрузка кадра при
  открытии формы разметки.
- `Electrode.Layout.pas` — модель данных электродных пар и меток рыбы
  (голова/хвост), привязка пары к каналу (`ChannelIndex`), JSON round-trip
  (версия 2 формата). Хранит также метки «истинная позиция рыбы»
  (`TTruthMark`) в отдельном файле `<имяРазметки>_marks.json`
  (`SaveTruthMarksToJSON`/`LoadTruthMarksFromJSON`): позиция в относительных
  координатах, привязка к кадру/событию и 4 амплитуды.
- `Electrode.LayoutForm.pas` — форма разметки на статическом изображении
  (кнопка `Geometry` на главной форме); назначение канала каждой пары
  своим комбобоксом, кнопка «Локализовать (по пикам)», зелёные маркеры
  позиций рыбы на кадре; электрод рисуется в цвете его канала
  (`EodChannelColors`); живой маркер и батч-локализация показывают
  диагностику «активный канал ↔ ближайший электрод»; при живой позиции
  от рыбы к межэлектродным зазорам рисуются «линии тока» (толщина ∝
  |прогноз. амплитуда| канала, цвет = цвет канала); кнопка «Отметить
  истинную позицию» пишет метки в `*_marks.json` (для проверки на реальных
  данных, см. `--truth`); не компилируется в песочнице Free Pascal
  (использует FMX).
- `Electrode.Localization.pas` — модель диполь-поля рыбы (1/d^n) и
  итеративная локализация мультистартом; экспортированы
  `FieldContributionValue`/`PredictChannelValue` для отрисовки поля.
- `Electrode.SimLayout.dpr` — консольный симулятор раскладки электродов:
  генерирует синтетические события (та же модель поля, n=1.5) по сетке
  позиций, прогоняет их через реальные `ScanChannelAssignment` и
  `LocalizeMultiStart` и выдаёт ошибку локализации в см по каждой ячейке;
  выводит `--svg` (раскладка + теплокарта ошибки, серые ячейки = не
  сошлось) и `--report` (UTF-8). Позволяет наперёд оценить раскладку
  (свою из JSON или встроенный пресет `--preset`) и численно увидеть
  обмен каналов «зелёный ↔ оранжевый». Запуск:
  `Bin\Electrode.SimLayout.exe --preset recommended --svg LayoutResult.svg`.
  Режим `--truth marks.json` проверяет модель на РЕАЛЬНЫХ данных: читает
  метки «истинная позиция рыбы» (`*_marks.json`) вместе с привязанной
  разметкой (поле `layoutFile`), локализует каждое событие и сравнивает с
  кликом — ошибка в см, «активный канал ≠ ближайший к клику электрод»,
  зеркальная неоднозначность; пишет `TruthResult.svg` и отчёт. При
  `--layout` пары из JSON переводятся в см (по размерам аквариума из
  файла, иначе `--tank`) — иначе модель поля с `MinDist = 0.5 см` работала
  бы в относительных единицах и поле у стенок вырождалось.

Ключевые решения:

- Статичные изображения вместо видео для разметки электродов (этап 1).
- Относительные координаты (0..1 по обеим осям) вместо сантиметров; размеры
  аквариума применяются как множитель позже — это развязывает разметку по
  времени от знания геометрии аквариума.
- Отметка головы и хвоста рыбы на изображении — для визуальной проверки и
  оценки размера тела.
- Поля размеров аквариума необязательны для ХРАНЕНИЯ разметки, но
  локализация выполняется в сантиметрах (модель поля задаёт `MinDist`
  в см): если размеры не заданы, кнопка «Локализовать»/живой маркер
  сообщают об этом и ничего не считают.
- Кнопка «Отметить истинную позицию» сохраняет метку сразу в
  `<имяРазметки>_marks.json` рядом с разметкой; если разметка ещё не
  экспортирована в JSON — метки не пишутся (показывается подсказка).

Открытые проблемы:

- Автоматический подбор сопоставления канал↔электрод и полярности (+/-)
  реализован (`Electrode.Matching.ScanChannelAssignment`), но надёжность на
  реальных данных ещё не подтверждена — см. «Проверка алгоритмов» ниже.
- Симметричные раскладки электродов создают физическую (не численную)
  неоднозначность локализации; мультистарт смягчает, но не устраняет её
  полностью. Наиболее частое проявление — перепутанные каналы двух
  почти-симметричных пар (классика: зелёный ↔ оранжевый). Диагностируется
  строкой «сильный канал ≠ ближайший электрод» (живой маркер и итог
  батч-локализации) и «линиями тока» на кадре; чинится переключением
  каналов в комбобоксах пар.

### Проверка алгоритмов геометрии/локализации

На момент 2026-09 проверка проводилась на синтетических данных. В дополнение к
раннему случайному прогону появился воспроизводимый инструмент `Electrode.SimLayout`
(см. выше): он численно оценивает КОНКРЕТНУЮ раскладку пар на бумаге, до
физической постановки. Проверенные на нём встроенные пресеты (60×30 см):
симптоматика «зелёного↔оранжевого» воспроизводится как обмен каналов в
почти-зеркальных раскладках; медианная ошибка локализации ~10 см даже без
шума — потолок 4-канальной моно-полюсной модели, а не качество кода.
Договорённость — перейти на проверку по реальным записям; для этого в форме
разметки добавлена кнопка «Отметить истинную позицию» (`*_marks.json`), а в
`Electrode.SimLayout` — режим `--truth`, который сверяет предсказание модели
с этими метками и показывает ошибку в см. На момент этой записи реальные
тестовые данные ещё не собраны (инструмент проверен на синтетическом
marks-файле). Подсистему пока нельзя считать проверенной на реальных данных.

## Тестирование

На раннем этапе для проверки отдельных концепций (детектор, корреляция,
формат `.eodpk`) использовались отдельные тестовые программы (`Eod.Tests`,
`Eod.PeakTest`, `Eod.IpiTest`, `Eod.ExtractTest`, `TestPeakStoreFast`). После
сборки основного проекта в текущем виде эти программы не запускались и не
поддерживаются; их актуальность относительно текущего кода не подтверждена.

Регулярного regression/unit-тестирования в проекте сейчас нет. Соответствующие
пункты остаются открытыми в `TODO.md` («P0 — тестируемость и математическая
корректность»). Решение о том, нужны ли автоматические тесты, в каком объёме
и какой инфраструктурой — не принято, требует отдельного обсуждения.

## Сборка

- RAD Studio / Delphi 12 (Embarcadero Studio 23.0), FireMonkey, платформа Win32.
- Быстрый вариант — из корня проекта: `cmd /c _build.cmd`
  (вызывает `rsvars.bat` и `MSBuild.exe ReadEOD.dproj /p:Config=Debug /p:Platform=Win32`).
  Для Release поменять `Config=Release` внутри `_build.cmd`.
- Вывод: `Bin\ReadEOD.exe` (туда же попадают тестовые exe), DCU — `DCU\Win32\<Config>`.
- В `Bin\` лежат примеры `.eodpk` для ручной проверки.

Известные безвредные предупреждения компилятора (не ошибки, можно игнорировать):
`H2164 PeakPositions` (ShowPeak), `W1000 MessageDlg deprecated`,
`H2077 BestDistance` (TEodPeakList.FillAroundFrame).
